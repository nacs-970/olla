<objective>
Add two read-only inspection tools — `list_dir(path)` and `grep_files(pattern, path, recursive=False)` — that the model can call and have executed immediately, with no confirmation prompt, per INSPECT-01/02/03.

Purpose: Discovery (browsing directories, searching code) is currently only possible through the `shell` tool, which either sits on the CONFIRM tier or requires allowlisted binaries. Dedicated inspection tools let the model explore safely and instantly, matching `read_file`'s no-prompt precedent rather than `safety.check()`'s shell-argv policy.
Output: `src/olla/tools/inspect.py` (both tool adapters), unconfirmed dispatch branches in `src/olla/loop.py`, updated `SYSTEM_PROMPT` documentation, and passing unit/integration tests for both tools.

**Mechanism note (INSPECT-03 / D-09):** Per locked decision D-09 (CONTEXT.md), `safety.check()` is never touched or given a new tool-name branch — `list_dir`/`grep_files` bypass it entirely via unconfirmed dispatch straight from `run_loop()`/`_prepare_action()` in `loop.py`, exactly like `read_file` today. ROADMAP.md's success-criterion 3 and REQUIREMENTS.md's INSPECT-03 line have been updated to describe this delivered mechanism directly, so a downstream verifier reading either canonical source will check `loop.py`'s dispatch branches and the zero-`Confirm.ask()`-calls tests below, not a `safety.py` `ALLOW` branch.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Model output -> tool arguments | `pattern`, `path`, and `recursive` in `<args>` are fully model-controlled (and, transitively, attacker-controlled if the model is echoing injected content it read earlier) before reaching `list_dir()`/`grep_files()` |
| Tool output -> next model turn | Directory names, file names, and grep match text returned by these tools become input to the model's next reasoning turn |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Denial of Service | `grep_files()` regex compilation | high | mitigate | `re.compile(pattern)` wrapped in `try/except re.error`, returns a `ToolResult` error dict instead of raising — any malformed model-supplied pattern must not crash the whole `run_loop()` session (Task 2) |
| T-05-02 | Denial of Service | `grep_files()` regex matching (ReDoS / catastrophic backtracking, CWE-1333) | medium | accept | No backtracking-complexity mitigation added this phase; accepted given the single-user local-CLI threat model, comparable to `src/olla/safety.py`'s existing accepted class of local footgun risk (research explicitly recommends accept, not mitigate, at this severity) |
| T-05-03 | Information Disclosure | `list_dir()`/`grep_files()` path argument (path traversal, CWE-22) | low | accept | Pre-existing, documented project posture (`.planning/codebase/ARCHITECTURE.md` "Working directory" note) — no containment boundary on any tool today (`read_file`/`write_file`/`shell` included); D-10 explicitly chooses no path pre-validation, so this phase introduces no new gap |
| T-05-04 | Tampering | `list_dir`/`grep_files` output fed back to the model (indirect prompt injection via file/dir names or matched line text) | high | mitigate | Both tools' output is recorded via `_record_file_observation()` (the same `<untrusted_file_content>` wrapper `read_file` already uses), preserving `untrusted_observation_seen` so any destructive shell/write action immediately following re-confirms even under `--yes` (Tasks 1 and 2) |
| T-05-05 | Information Disclosure | `.git` internal object scanning surfacing packed/compressed binary noise in grep output | low | mitigate | D-08's `.git`-exclusion is enforced in `grep_files`'s recursive traversal via in-place `dirnames[:]` pruning (Task 2); `list_dir` intentionally still shows `.git` as a visible entry (D-05) — these are deliberately different, not conflated |
