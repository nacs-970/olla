From src/olla/parser.py (full file, 32 lines — this plan modifies, Pitfall 1 fix):
```python
"""Tolerant XML-tag parser for <tool>/<args>/<final> model output."""

import re

FINAL_RE = re.compile(r"<final>(.*?)(?:</final>|$)", re.DOTALL | re.IGNORECASE)
TOOL_RE = re.compile(r"<tool>(.*?)(?:</tool>|$)", re.DOTALL | re.IGNORECASE)
ARGS_RE = re.compile(r"<args>(.*?)(?:</args>|$)", re.DOTALL | re.IGNORECASE)


def parse_response(content: str) -> dict:
    """Tolerantly extract <tool>/<args>/<final> from model output.

    Strips markdown code fences, then prefers <final> if present, else a
    complete <tool>+<args> pair, else returns the original raw content.
    """
    stripped = re.sub(r"```[a-zA-Z]*\n?|```", "", content)

    final_match = FINAL_RE.search(stripped)
    if final_match:
        return {"type": "final", "text": final_match.group(1).strip()}

    tool_match = TOOL_RE.search(stripped)
    args_match = ARGS_RE.search(stripped)
    if tool_match and args_match:
        return {
            "type": "tool",
            "tool": tool_match.group(1).strip(),
            "args_raw": args_match.group(1).strip(),
        }

    return {"type": "none", "raw": content}
```

PROBLEM (Pitfall 1): line 16's `re.sub(r"```[a-zA-Z]*\n?|```", "", content)` runs on the ENTIRE `content` string before `ARGS_RE` extracts `args_raw`. For `write_file`, `args_raw` is `path\n<file content>` — if the file content itself contains a code fence (literal ` ``` ` sequences, e.g. the model is writing a markdown file or a Python file containing a fenced block), those get deleted from the written content. Additionally, line 28's `.strip()` on the whole `args_raw` strips a meaningful trailing newline from the file content (many files should end with `\n`).

MANDATED FIX (Option A — tool-conditional handling; no open choice, implement exactly as follows):

For `shell`, `read_file`, and any other tool, `parse_response` behaves EXACTLY as it does today: the global fence-stripping `re.sub` runs over `content` before extraction, and `args_raw = args_match.group(1).strip()`. This is a strict no-op for every existing call site — in particular, 03-01's `read_file(parsed["args_raw"])` (Task 2 step 7 of 03-01-PLAN.md) requires ZERO changes and continues to receive a stripped single-line path exactly as before.

Only `write_file` is special-cased. Implementation shape:

1. Determine `tool_name` BEFORE applying the global fence-stripping: run `TOOL_RE.search(content)` against the ORIGINAL `content` (not the fence-stripped `stripped` string) to get `tool_match`. Also run `ARGS_RE.search(content)` against the ORIGINAL `content` to get `args_match`. If `tool_match and args_match` are BOTH present AND `tool_match.group(1).strip() == "write_file"`, take the write_file path below. Otherwise (no `tool_match`, no `args_match`, or `tool_match.group(1).strip() != "write_file"`), fall through to the existing, unchanged behavior using `stripped = re.sub(r"```[a-zA-Z]*\n?|```", "", content)` as today — this mirrors the existing combined-guard pattern (`if tool_match and args_match:`) used for all other tools, so `<tool>write_file</tool>` with no `<args>` tag falls through to `{"type": "none", "raw": content}` without raising.
2. write_file path: with `args_match` already obtained and confirmed non-None in step 1, set `args_raw = args_match.group(1)` VERBATIM — no `.strip()`, no fence-stripping applied to this matched span. `tool_match.group(1).strip()` (from step 1, computed against original `content`) gives `"write_file"` for the `"tool"` key.
3. Return shape is unchanged in both branches: `{"type": "tool", "tool": tool_match.group(1).strip(), "args_raw": ...}` — no new dict keys (PATTERNS.md "do NOT add new keys" constraint holds; the path/content split on `args_raw` happens in `loop.py` via `partition("\n")`, per Task 2 step 6 below).
4. `final_match` handling (the `<final>` branch) is unaffected — it continues to run against fence-stripped `content` as today, since `<final>` text is never multi-line file content.

Why this passes `test_markdown_fence_tolerance` (tests/test_parser.py lines 16-19, MUST KEEP PASSING):
```python
def test_markdown_fence_tolerance():
    content = "```\n<tool>shell</tool><args>echo hi</args>\n```"
    result = parse_response(content)
    assert result == {"type": "tool", "tool": "shell", "args_raw": "echo hi"}
```
`tool_match.group(1).strip()` here is `"shell"`, not `"write_file"`, so this test takes the unchanged-behavior branch (fence-stripping over `content` first, exactly as today) and passes identically to the current implementation. `TOOL_RE.search` and `ARGS_RE.search` use `re.DOTALL` and `.search()` (not `.match()`), so they find `<tool>...</tool>` / `<args>...</args>` regardless of leading/trailing ` ``` ` lines in `content` — the wrapping fences in this test sit OUTSIDE the `<tool>`/`<args>` spans entirely, so searching the original vs. fence-stripped `content` for `tool_match`/`args_match` makes no difference for non-write_file tools.

For `write_file`, fences and trailing newlines INSIDE the `<args>...</args>` span (i.e., part of `args_raw` itself) are now preserved verbatim, satisfying the new write_file requirements below without touching any of the other 6 existing parser tests (`test_final_tag`, `test_tool_and_args`, `test_surrounding_prose_tolerance`, `test_unclosed_args_tag_tolerance`, `test_no_recognizable_tags`, `test_final_wins_over_tool`) — none of these use `tool == "write_file"`, so all take the unchanged-behavior branch.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model output -> loop dispatch | Model-supplied `<args>` (path + file content) crosses from untrusted model output into `write_file(path, content)` |
| loop -> filesystem | `write_file` performs a real, irreversible filesystem mutation (overwrite or create) |
| model output -> SYSTEM_PROMPT contract | `</args>` appearing literally inside model-generated file content interacts with the `call_model` stop-sequence (Pitfall 5) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-04 | Tampering | `loop.py` write_file dispatch | mitigate | Path traversal / arbitrary-file-overwrite (e.g. model supplies `../../etc/cron.d/x` or an absolute path outside the project). Mitigated via the confirm-gate (SC2): `Path(path).resolve()` is computed and shown to the user BEFORE any write occurs, so the user sees the true destination (including traversal resolution and symlink follow-through) and can decline. This is NOT a path-containment jail (Pitfall 4 — explicitly rejected by RESEARCH as inconsistent with the shell tool's existing unsandboxed model); the confirm-gate is the boundary, consistent with Phase 2's design for shell. |
| T-03-05 | Tampering | `loop.py` write_file dispatch | mitigate | Symlink redirection — if `path` is a symlink, `Path(path).resolve()` follows it to the real target and that resolved path is what's shown in the confirm prompt, so the user is not misled about which file is actually being overwritten. |
| T-03-06 | Tampering / Repudiation | `loop.py` write_file dispatch | accept | Overwrite-without-notice — `write_file` does not distinguish "create new file" from "overwrite existing file" in the confirm prompt. Accepted for v1: not required by FILE-02's stated success criteria (SC2 only requires the resolved path be shown), and the resolved path itself gives the user enough information to recognize an existing file's location. Deferred as a possible future enhancement, not a Phase 3 gap. |
| T-03-07 | Elevation of Privilege | write_file -> subsequent shell | accept | Write-then-exec chain (model writes a script via `write_file` then executes it via `shell`). Out of scope for Phase 3 — both the write and the subsequent shell execution are independently confirm-gated (write_file here, shell's CONFIRM/BLOCK tiers from Phase 2); no new compounding risk introduced by adding write_file beyond what Phase 2 already accepted for shell. |
| T-03-08 | Tampering / Repudiation (unintentional) | `call_model` stop-sequence vs. write_file content | accept | Pitfall 5 — if model-generated file content contains the literal substring `</args>`, `ollama.chat`'s `stop=["</args>", ...]` truncates generation at that point, silently producing an incomplete file write. Mitigated via documentation only: `SYSTEM_PROMPT` (this plan, Task 2 step 7) instructs the model not to emit literal `</args>` in file content. No automated regression test is possible (mocked `ollama.chat` bypasses real stop-sequence behavior) — captured as a Manual-Only Verification in 03-VALIDATION.md, not a Wave 0 gap. |
