<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model output -> `search_web` query argument | The model chooses an arbitrary query string sent verbatim to a third-party search endpoint |
| DuckDuckGo Lite response -> olla process | Response HTML (including a possible anti-bot challenge page) is parsed and fed back into the model's context |
| search_web output -> subsequent tool-call trust state | Snippet text is adversary-influenced (any page can appear in results); must not be treated as trusted user input by a later loop step |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-03 | Tampering / Elevation of Privilege | `search_web` output -> `loop.py` message history (prompt injection via untrusted web content) | high | mitigate | WEB-04: reuses plan 06-01's `_record_web_observation` wrapping in `<untrusted_web_content>` and `untrusted_observation_seen` gate — same mechanism, now also wired for `search_web` (this plan's Task 1). |
| T-06-05 | Tampering (bot-challenge/malformed response silently mis-parsed as empty results) | `search_web` (`src/olla/tools/web.py`) | low | mitigate | Detect the absence of `result-link` anchors combined with anomaly-page markup and return `{"error": ...}` instead of an empty/fabricated result list — makes the failure mode legible to both the model and a human debugging it (this plan's Task 1). |
| T-06-06 | Tampering (sponsored/ad content shipped as organic results) | `search_web` DDG Lite parsing (`src/olla/tools/web.py`) | low | mitigate | Discriminate on `<tr class="result-sponsored">`, never on the anchor's `class="result-link"` alone (both sponsored and organic anchors share that class) — verified by a fixture-based test in this plan's Task 1. |
| T-06-04 | Denial of Service (local host resource exhaustion) | `search_web` DDG Lite response body (`src/olla/tools/web.py`) | medium | mitigate | `search_web` calls the same `_read_capped()` byte-ceiling helper (`_MAX_RESPONSE_BYTES`, built in plan 06-01's Task 1) as `fetch_url` — a plain buffering `client.get()` is not used here even though DDG Lite pages are small in practice, because both tools share the same RAM-constrained host (`STATE.md`: a 7.2GB model already OOM-killed on this host's 7.1GB RAM).
