<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Terminal input (`session.prompt()`) → slash-command dispatch | user-typed control-plane input, a different and more-trusted tier than model-generated tool output |
| `messages`/tool observations → slash-command dispatch (must NOT cross) | model-generated content must never be interpreted as REPL control commands |
| `prompt_toolkit` `FileHistory` file → disk | new persistent on-disk state this project has never had before |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-01 | Spoofing | `src/olla/repl.py` slash-command dispatch | high | mitigate | Dispatch checks only the raw `session_prompt.prompt()` return value before any `run_loop()` call; never scans `session_state.messages`/tool-observation text for slash-command-shaped strings (Task 2; `test_slash_command_in_tool_observation_does_not_dispatch`). |
| T-07-04 | Information Disclosure | `prompt_toolkit` `FileHistory` file | medium | accept | Standard `prompt_toolkit`/shell-history behavior — a user pasting a secret into the REPL writes it to a plaintext history file, same class of risk as any shell history file. Documented as a known limitation via a one-line code comment in `repl.py`; building a redaction system is out of scope this phase (consistent with the project's existing `mask_secret()` being scoped to CLI-flag/debug-log paths only, not free-form REPL input). |
</threat_model>
